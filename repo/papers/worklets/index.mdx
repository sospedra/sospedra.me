Block the JavaScript thread of a React Native app with a `while(true)` and watch a Reanimated gesture keep tracking your finger at 60fps. That shouldn't be possible. The animation is written in JavaScript and the JavaScript thread is dead. The trick: your app runs **two JavaScript runtimes**, and the second one lives on the UI thread.

## The second runtime

The design goes back to Krzysztof Magiera's [Introducing Reanimated 2](https://swmansion.com/blog/introducing-reanimated-2-752b913af8b3): instead of a declarative animation DSL (Reanimated 1's approach) or native driver whitelists, spawn a secondary JS context on the UI thread and run real JavaScript there. Functions marked as worklets execute in it:

```js
const style = useAnimatedStyle(() => {
  'worklet'
  return { transform: [{ translateX: offset.value }] }
})
```

The `'worklet'` directive is a compiler hook. The [babel plugin](https://github.com/software-mansion/react-native-reanimated/blob/2.14.4/plugin.js) finds these functions and rewrites each into a factory. This is roughly what ships in your bundle in the 2.x line:

```js
const _f = function () {
  return { transform: [{ translateX: offset.value }] }
}
_f._closure = { offset }              // captured variables, by name
_f.asString = 'function _f(){...}'    // source, re-evaluated on the UI runtime
_f.__workletHash = 1234567            // identity across runtimes
_f.__location = '/app/Box.js (12:4)'
```

A worklet is code-as-string plus a captured-value bag, rebuilt inside the second runtime. Two phases people conflate: the plugin extracts the closure's *identifier list* at build time; the *values* are copied when the worklet is instantiated and shipped across. That copy is the root of every gotcha below. (In [Reanimated 3](https://github.com/software-mansion/react-native-reanimated/releases/tag/3.0.0), released this February, the string-and-eval mechanism became "shareables": the function and closure are recursively cloned into C++ representations, reconstructed once per runtime, no eval. Same model, sturdier plumbing.)

You rarely write the directive yourself: `useAnimatedStyle`, `useDerivedValue` and Gesture callbacks are auto-workletized by the plugin. Inside one, `global._WORKLET === true` if you want to check where you are.

## Shared values, the actual bridge

Two runtimes need shared memory. That's what [shared values](https://docs.swmansion.com/react-native-reanimated/docs/2.x/fundamentals/worklets/) are: C++-backed host objects, reachable from both runtimes over JSI, no serialization on the hot path. The classic RN bridge (async, batched, JSON) never enters the picture, and that's the whole 60fps secret. Not faster JavaScript. Closer JavaScript.

```js
const offset = useSharedValue(0)

const pan = Gesture.Pan()
  .onChange((e) => {
    // runs on the UI runtime
    offset.value += e.changeX
  })
  .onEnd(() => {
    offset.value = withSpring(0)
  })
```

Assign to `.value` from a worklet and the animated style reacts on the same frame. No setState, no render, no reconciliation. React never wakes up.

## The gotchas, and they bite

1. **Closures are copied, not referenced.** Mutate a captured plain object from the React side and the worklet won't see it; it has its own copy. Shared values exist precisely to opt out of copy semantics.
2. **Big captures cost real money.** Everything in `_closure` serializes at worklet instantiation. Capture a 2.000-item array in a gesture callback and you built a frame-time bomb. Keep captures scalar.
3. **Crossing back is explicit.** A regular function doesn't exist on the UI runtime; calling it from a worklet throws. `runOnJS(fn)(args)` schedules it back on the React runtime, asynchronously, by handle, which is also why `fn` must be a stable top-level reference and why you can't await its result mid-gesture:

```js
.onEnd(() => {
  runOnJS(onGestureFinished)()
})
```

4. `console.log` inside a worklet works, but it's a `runOnJS` in a trenchcoat. Log per frame and you'll profile the mystery jank you created.

The dogma was one JS thread orchestrating native views over an async bridge. Worklets quietly break it: run the latency-critical 5% of your JavaScript on the UI thread, keep React for the other 95%. The second runtime is not going away; learn its physics now.
