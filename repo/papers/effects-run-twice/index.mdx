You upgraded to React 18. Your effects fire twice. Your fetch runs twice, your analytics event doubles, your WebSocket connects twice. Before you open the issue: it's [documented](https://reactjs.org/docs/strict-mode.html#ensuring-reusable-state), it's dev-only, and it's a test you're failing, not a bug you found.

## What StrictMode actually does

The folklore says "React mounts, unmounts, and mounts again". Close, and wrong in a way that matters. React does **not** remount anything. After the first commit, in development, the reconciler walks the fibers flagged for it and runs your effect cleanups, then your effects again: layout cleanups, passive cleanups, layout setups, passive setups, in that order. The function doing it is literally called [`commitDoubleInvokeEffectsInDEV`](https://github.com/facebook/react/blob/v18.0.0/packages/react-reconciler/src/ReactFiberWorkLoop.new.js) in the reconciler source. No second render pass, no fiber deletion. **State, refs and DOM all survive.** It's a rehearsal of "effects destroyed and re-created on a mounted component", not a remount.

Why rehearse that? Because the team is building an [Offscreen API](https://github.com/reactwg/react-18/discussions/19): React detaches a tree (tab away, virtualized list, back navigation) and later reattaches it *with state preserved*, re-running effects on reappear. The production twins of the dev rehearsal already exist in the same source file, `disappearLayoutEffects` and `reappearLayoutEffects`, and Suspense already uses them: the v18 [changelog](https://github.com/facebook/react/blob/main/CHANGELOG.md) says it plainly, "make Suspense remount layout effects when content reappears". So the question StrictMode asks is precise: **can your effect setup/cleanup cycle run twice with the same deps and leave the world identical?**

## The failing patterns

The [working group thread](https://github.com/reactwg/react-18/discussions/18) enumerates the shapes. They reduce to three:

```js
// 1. Effect without cleanup. The zombie.
useEffect(() => {
  socket.connect()
}, [])
```

Two setups, two sockets, zero teardowns. The fix is symmetry:

```js
useEffect(() => {
  socket.connect()
  return () => socket.disconnect()
}, [])
```

```js
// 2. The uncancelled fetch. The race.
useEffect(() => {
  fetch(`/api/user/${id}`).then((r) => r.json()).then(setUser)
}, [id])
```

Double-fire makes the race visible, but it was always there: change `id` fast and the slow response overwrites the fresh one. `AbortController` closes both holes. Swallow only the abort, not real failures:

```js
useEffect(() => {
  const controller = new AbortController()
  fetch(`/api/user/${id}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch((e) => {
      if (e.name !== 'AbortError') throw e
    })
  return () => controller.abort()
}, [id])
```

```js
// 3. The once-guard. The framework fight.
const didInit = useRef(false)
useEffect(() => {
  if (didInit.current) return
  didInit.current = true
  initAnalytics()
}, [])
```

Here's where the "no remount" mechanics bite. The double-invoke never resets refs, so `didInit.current` is still `true` on the second run and the guard "passes" the rehearsal. Feels like a win. Now play it forward to Offscreen: hide the tree, reattach it, effects re-run with refs preserved, and your guard turns reconnection into a permanent no-op. The socket never comes back. StrictMode rehearsed exactly the case your guard breaks, and the guard cheated the rehearsal. App-level one-time init belongs at module scope, next to `createRoot`, where the problem dissolves.

## Two footnotes for the curious

The rehearsal runs during the passive-effect flush, **after paint**. A first mount runs layout effects before paint. If you measure DOM in a layout effect, the second invocation behaves differently on the timeline; another reason measurement belongs in refs-on-render or `useLayoutEffect` with idempotent math.

And the double *render* (not effects) isn't new: component bodies and `useState` initializers double-invoke since 16.3. React 17 silenced the second `console.log`, [people hated it](https://github.com/facebook/react/issues/21783), and 18 [un-silenced it](https://github.com/reactwg/react-18/discussions/96); DevTools now dims the duplicate grey instead.

StrictMode's double-invoke is a free idempotence fuzzer running on every save. Effects that survive it survive fast refresh, survive `id` changing mid-flight, and survive the [Offscreen future](https://reactjs.org/blog/2022/03/29/react-v18.html). Don't silence the alarm. Fix the kitchen.
