# sige defect ledger

Every defect found on `apps/sige`, what it belonged to, how it was fixed, and
what proves the fix. Read the class table FIRST whenever a new defect appears.
If the new defect lands in a class that already has several entries, the patch
is not the answer. The class needs a systemic fix.

The gospel (`2026-08-06-sige-remediation.md`) is the ORDER OF WORK. This file is
the RECORD OF DEFECTS. They are different documents and neither replaces the other.

**Class D is the standing structural problem.** SIGE's whole point is that a
keyless outsider can check the operator. Ten times now, a check has read its
expected value from something the operator controls.

Round ten sharpened the rule and it is worth stating exactly. D03 moved the
enrollment binding under a signature the HSM gates make. That was necessary and
it was not sufficient, because a signature over a value is not a check of it.
Both gates signed a pin neither gate read, so the operator forged the record
before the order and the reviewers signed his pin along with it. D24 is the real
fix: the gate needs enrollment-time MEMORY, not just a field in the pre-image.

So the question to ask before any class-D patch is now two questions. Which key
already signs a value that could carry this binding? And what state does the
signer hold that lets it refuse a value it should never sign?

**Class C is the standing process problem.** The mutation rule in the gospel
exists because of it. It has not stopped the class from growing, because the
rule was applied per commit, not per changed line. D22 extends it: the harness
that runs a mutation is itself untested, so a mutation result needs the same
scepticism as a green test. A mutation that reddens tests it cannot reach is a
broken harness, not a broad guard.

## How to use this file

1. A new defect appears. Find its class in the readout above.
2. If the class count is already 3 or more, do not write the patch yet. Name the
   property that keeps producing the class, and say whether this fix addresses
   it or adds another entry.
3. Add the row. Fill `Fix` before writing code and `Proof` after the mutation.
4. Update the class count.
